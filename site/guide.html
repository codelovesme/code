The Code guide

Code is a constraint-based language: variables narrow a domain of possible values instead of being assigned, reusable logic is handler dispatch rather than functions, and a program's result is its final bindings — there is no print. Every example below is a real program from the repository, run in CI exactly as shown. Try any of them in the playground — no install needed.

02 Constraint variables

This is the idea the whole language turns on. A variable doesn't hold one slot you overwrite — it holds a domain, the set of values it could still be. Each constraint you add narrows that domain. When the domain shrinks to exactly one value, the variable is resolved and usable.

__EXAMPLE__02_constraint_variables__
Assignment is a special case. y = 5 isn't a different operation from x > 10 — it's the same narrowing, taken all the way to a domain of one value in a single step. That's why the language has one model, not two.

03 Single assignment

At the top level, each name is bound once. This is checked, not just encouraged — a second a = … is an error, never a silent overwrite. Combined with no recursion and only bounded loops (§06), it's what lets a program's total work be known before it runs.

__EXAMPLE__03_single_assignment__
There is exactly one place reassignment is allowed: inside a handler body, as local bookkeeping while it computes its response. Everywhere else, a name means one thing for the whole program.

04 Types

A type is a named schema — field names paired with constraints. Constructing a value checks it against the schema. Types compose with ∪ (union — either) and ∩ (intersection — both), the same set operators you'd write on paper.

05 Handlers, not functions

Code has no user-defined functions — there is no name(args) call syntax anywhere in the grammar. Reusable logic is a handler: a particle type paired with a response block. You invoke it by emitting a particle at a target and collecting the result with get.

__EXAMPLE__05_handlers__
Why no functions? One dispatch mechanism (emit X to target get result) composes across modules and message boundaries the same way it works in one file — so there's nothing a function would add that a handler doesn't already cover.

06 Loops

There's one loop form: loop <var> over <array> get <result>. No while, no counters, no recursion. A loop runs exactly as many times as the array is long — a count known before it starts — and yield collects values into the named result.

__EXAMPLE__06_loops__
The absence of unbounded looping isn't a missing feature — it's the guarantee. Every program's total work is statically bounded because there's no construct that can run an unknown number of times.

08 No core I/O

The interpreter never writes to stdout. There is no print, no console handler. A program's visible result is its final top-level bindings — which is exactly what the playground's result panel shows, and why that panel is the natural way to read a program's output.
