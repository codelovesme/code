why code

Language overview

Values, handlers and modules form the language model. Explore these details after your first program, or open the full reference below.

Six value types

Number, String, Boolean, Null, Array, Object — exactly JSON's. The two containers stay distinct: arrays are ordered, objects compare by field name.

Types from values

x = … introduces or reassigns a name; nothing may shadow it. Variables, fields, and list elements keep their first non-null type. To allow another, label it up front: x ∈ Number ∪ String = 1.

A faster interpreter

The playground uses v__ENGINE_VERSION__’s register-bytecode interpreter, with typed number operations, compiled to WebAssembly. It runs here in your browser.

Build once, reuse the build

code run builds and caches a native executable for fast starts at native speed. Choose --interpret to interpret, or code build for an artifact. Both paths have the same behavior, enforced by tests.

Particles

Point { x = 1 } is an object with a _class tag — dispatched by emit, no schema required.

Loops & conditionals

loop x over arr, if, and break, with indented bodies. Braces make objects. No while, no else — ever.

Named data types

type Color = "red" ∪ "green" names a set of values. Combine labels with ∪, leave object fields open with …, and ask membership at run time with ∈. Types can describe nested and recursive data.

Native numbers

Native compilation is close to C/Rust on the measured numeric loop in public v2.23.2. Broader workloads, runtime modes and snapshot memory are measured separately. See the measurements.

Capabilities are modules

Keep I/O explicit: code install console, then link it. Modules cover files, HTTP, databases, browser DOM and canvas, and more. Swap a mock in for fixtures; a handler reports failures as an Exception particle.

take it with you

Tools and integration

The playground is the same interpreter you can ship yourself. Embed code in a web app, build a native module without leaving the language, write one in Rust, or in anything else that produces a C-ABI shared library.

Platform: the playground and code-wasm run anywhere. The prebuilt code CLI and native module assets are Linux x86_64, for now; browser modules also have wasm32 archives. Building the CLI from source needs Rust and LLVM 17.

CLI · native & wasm

code — run, build, check

Start with a file or a project. Repeated runs reuse the cached native build; without a build toolchain, the interpreter remains the fallback.

1 get the CLI

Download the Linux x86_64 archive from the latest release, or build this repository with Rust and LLVM 17:

cargo build --release --workspace
2 make a project and run it
code init demo
cd demo
code run
code build --release
3 keep it checked
code check
code format --check .
mkdir tests
cp main.code tests/start.code
code test

The first build is part of the first run. Small programs build optimized immediately; larger ones can start on a quick build while the optimized one is prepared. code run --strict checks known contracts before running.

euglena · applications

Build an app on top of code

Euglena adds app manifests and shared gene files over the code toolchain, for native and browser applications.

A manifest describes the app’s dependencies and configuration; Euglena assembles its entry program and delegates language work to code. The language stays small, while the app layer handles how the pieces are wired.

Use the language by itself for a script or module, or use Euglena when the application needs that extra structure.

npm · browser & node

code-wasm — run code in any JS host

The real parser + interpreter as a small WASM bridge. One call per program, synchronous results, and third-party modules as plain JS callbacks.

1 install
# bundler (Vite, webpack, Rollup…)
npm install code-wasm@2.23.2

# …or straight from a CDN, no build step
import init, { run, run_with_modules } from "https://esm.sh/code-wasm@2.23.2";
2 run programs
await init();
console.log(run("a = 5\nassert a = 5\n"));
// "" — success is the empty string; a failed assert or parse
// error returns "error: ..." instead. No core I/O means no dump
// of bindings — a program's output is whatever it emits itself.
3 link modules from your app
const modules = {
  math: {
    dispatch(particleJson) {
      const p = JSON.parse(particleJson);
      if (p._class === "Double")
        return JSON.stringify({ _class: "DoubleResult", value: p.value * 2 });
      throw new Error("unknown handler");
    },
  },
};
run_with_modules(
  'link "math" as m\nemit Double { value = 21 } to m get r\n' +
  "assert r.value = 42\n",
  modules,
);

Everything crosses that boundary as JSON strings — a module backed by a plain function works exactly like one backed by a real .wasm file. For run_with_modules, provide every module up front; this JS bridge does not load native libraries.

Write the module in code itself

No second language. Asking for the container is asking for the library — a file's handlers become code_module_dispatch, its top-level names stay private, and another code program links the result exactly like a native one.

1 write it
| greet.code
Greet { who ∈ String } =>
    return Reply { text = "hello " + who }
2 build it as a library
code build greet.code --target shared -o libgreet.so
# --target static -o libgreet.a for an archive instead
3 link it from another program
link "libgreet.so" as g
emit Greet { who = "ada" } to g get r
assert r.text = "hello ada"

A link reaches the file's handlers; its top-level names stay private, the same rule a source link follows. The result works from code run or code build on the consuming side, no different from a module written in Rust or C.

crates.io · rust → .so

code-native — write native modules in Rust

Safe builders over the real ABI, plus the runtime linked in for you — no checkout of this repo needed. Your crate builds into a .so that both code run and code build accept.

1 set up the crate
# Cargo.toml
[lib]
crate-type = ["cdylib"]

[dependencies]
code-native = "2.23.2"
2 implement two exports
use code_native::*;

#[no_mangle]
pub extern "C" fn code_module_abi_version() -> u32 {
    CODE_ABI_VERSION
}

#[no_mangle]
pub unsafe extern "C" fn code_module_dispatch(out: *mut CodeValue, particle: *const CodeValue) {
    guarded(&mut *out, "mymodule", |out| match read_field_str(&*particle, "_class") {
        Some("Double") => {
            let v = read_field_number(&*particle, "value").unwrap_or(0.0);
            make_result(out, c"DoubleResult", |slot| number(slot, v * 2.0));
        }
        _ => null(out),
    });
}
3 build & link it from code
cargo build --release   # → target/release/libmymodule.so

| my_script.code
link "libmymodule.so" as m
emit Double { value = 21 } to m get result
assert result.value = 42

An optional third export, code_module_vars, makes m.someConst work alongside emit. C (and anything else that produces a C-ABI shared library) uses src/code_abi.h directly — modules are distributed through release assets and installed with code install.

template · publish your own

Ship a module other people can install

A working module, its fixture, and the CI that publishes it — copy it, rename it, replace the handler. Nothing central to register with and no permission to ask for.

1 start from the template
# templates/module/ in the repo
cp -r code/templates/module my-module
cd my-module && cargo build --release
2 prove it in both output modes
cp target/release/libgreet.so tests/greet.so
code run   tests/greet.code
code build tests/greet.code -o /tmp/g && CODE_CHECK_LEAKS=1 /tmp/g
3 tag it
git tag v1.0.0 && git push --tags

CI builds the artifact, checks it loads through both modes, writes the module.json that code install reads, and attaches it all to a GitHub Release. Share the URL.

Modules are GPL-3.0. Every native module embeds the language's runtime.c — that is how the ABI's value-lifetime contract works — so a module is a derivative work. Worth knowing before you write one, not after.
