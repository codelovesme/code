# Splitting a program while keeping each file's variables private (ticket 101)

**Owner decision, 2026-11-04:** keep every source file's variables private.
Use the language's existing handler/particle model to split large files.
The earlier proposal for same-module shared source scope was rejected and
never implemented. No new link syntax, exports or shared bindings are needed.

A normal source link contributes handlers to the program-wide dispatch table;
it does not expose that file's variables. One file owns persistent state and
updates it in response to command particles. Another asks a query handler for
the data it needs and renders the returned value. Text/formatting handlers
receive their inputs explicitly and return their result.

For example, a state file:

```code
query = ""
SearchChanged { value } =>
    query = value
    emit Draw to this
    return Noted
GetViewState => return ViewState { search = query }
```

A view file:

```code
Draw =>
    emit GetViewState to this get state
    | Build the screen from state.search and emit it to the dom module.
    return Drawn { search = state.search }
```

The view's `state` is a handler-local value, not an alias to the owner's
binding or a persistent cache of application state. The next query reads the
owner's latest values. Arrays and objects retain Code's existing value
semantics: changing a returned snapshot does not change the owning file.
Only the owner handles mutations. For a one-shot focus request, for example,
a view can acknowledge it with an `EditorFocusDrawn` command; it cannot clear
another file's flag by assignment.

Query responses should contain the presentation data the view needs. A token
used for network requests stays with the state owner; the view can receive a
Boolean saying whether the reader is signed in. Avoid returning unrelated
state or carrying large snapshots through every row-rendering call: choose
small query results or pass one already-read snapshot to a render subtree.

This is application design using existing language behavior, not a new
runtime feature. Initialization order, private scopes, module depth, `to base`,
no-shadowing and ordinary value semantics all retain their current rules.
A top-level expression still runs once; handlers recompute dynamic values.

For Euglena, independent state, views and text genes are ordinary source
links generated by its existing CLI. No manifest-level shared-scope option
or special handling in Code is required. Todo is the concrete example in
my-euglena-apps ticket 101; its installed palette/outbox genes also keep
their own state and communicate through handlers.

## Visibility diagnostics

Code `6ba4fc2` identifies the loaded source file declaring an inaccessible
top-level binding when `run` or `build` refuses an undefined variable. The
hint does not make the binding visible. Only the loaded program is searched;
other handlers' locals and unlinked neighboring files are excluded.
`tests/linked_binding_diagnostics.rs` covers sibling modules, a child reading
its caller, and independent entries. Native/interpreted refusal stays equal.
